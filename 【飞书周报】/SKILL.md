# 飞书周报生成

## 数据收集（必须先做，不凭记忆编）

1. 扫描 git 提交：
   ```bash
   # ~/Downloads/代码（本人仓库）
   cd /Users/zhangxinyun/Downloads/代码 && for d in */; do
     [ -d "$d/.git" ] || continue
     git -C "$d" --no-pager log --all --since="<起>" --until="<止>" \
       --author="zhangxinyun" --date=short --pretty=format:"%h|%ad|%s"
   done
   # ~/Documents/ChatGPT（Codex 工作区，含 Chilis/小杨等）
   # 同样方式扫描，两个来源合并
   ```
   - 日期范围：周报=上周五~本周四左右（以用户说"这周"当天为界往前推 7 天）；日报=当天往前 5 个工作日
2. 剔除同事提交（--author=zhangxinyun 已过滤）；同哈希提交出现在多个品牌仓（共享 EOS 代码）只算一次，标注"与 XX 同代码共享"
3. 对照记忆库里的本周项目动态（生产事故、发版、撤回等）补充 git 看不到的内容

## 范围铁律

- **排除项目**：HK（HelloKitty）、满记、SPH（商铺好）——有独立汇报线，用户明确要求不写
- **不写 AI 工具链**：Codex 桌面端定制、技能整理、网络治理等研发效能内容，用户明确说不写进周报
- **下周计划里不放已经发过/沟通过的遗留项**（如已单独汇报过的发版、扩容事项），只放新任务；拿不准就问

## 模板（结构与工时格式不可变）

```
**本周工作汇总（M/D ~ M/D）**

**1. <项目名>**（预计 Xh ｜ 实际 Yh ｜ ✅ 完成）
- **<专项名>**（预计 Xh ｜ 实际 Yh）：<一句话结果+上线状态>——<超时/延期原因，如有>
- <普通分项>（预计 Xh ｜ 实际 Yh）：<内容>

**2. ...**（按工作量从大到小排，本周重心放第 1）

**工时合计：预计 Xh ｜ 实际 Yh**

**下周计划**

**1. <项目名>·<专项>**（预计 Xh）
- <分项>（Xh）
- ...

**2. ...**

**3. 线上支持与日常事务**（预计 5h）
- 各项目线上问题响应与排查（3h）
- 发版窗口支持与发版后验证（2h）

**下周预计合计：Xh**
```

## 工时规则

- **本周**：每项给预计/实际双工时；状态用 ✅完成 / ⚠️部分完成（注明外部阻塞）；突发任务写"预计 0h ｜ 实际 Xh，突发"；超时的如实写原因（排查深、方案试错撤回），反而体现代价与处置
- **下周**：必须排满整周 **~50h**（用户实际工作节奏含加班，42h 会被打回"怎么够"）；专项拆细：方案设计/后端开发/联调/测试发版分开列；**联调要按对接方单列**（如 POS 联调、OC 联调各一行）；末尾固定加"线上支持与日常事务 5h"兜底
- 常用工时档：方案设计 2-3h、DB 设计 2h、后端开发 6-12h、联调 3-6h、测试发版 3h

## 流程

1. 扫 git → 初稿（工时先按同类任务估）
2. 给用户过目，按反馈迭代（常见反馈：删某节/加联调明细/工时排满）
3. 定稿格式：纯 markdown，可直接粘飞书
